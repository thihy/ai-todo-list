# ADR-001: SQLite is the source of truth; files are projections

- **Status:** Accepted. Implemented.
- **Date:** 2025-08 (initial); refreshed 2026-09 (v17 tag catalog migration).

## Context

The app persists three different kinds of state:

- the user's work items (todos) and their structured metadata;
- rich content (progress HTML, notes, drawings, attachments);
- an offline AI conversation history (DSH sessions).

A naive design would split these across several file formats and
treat each as equally authoritative. The product surface — quick
filter, FTS5 search, tag autocomplete, archive / restore, AI tool
mutations — needs joins, indexes, and atomicity that are awkward
to maintain across files.

## Decision

- The single source of truth for *business* state is the SQLite
  database at `${dataDir}/db.sqlite` (WAL mode, foreign keys on
  after migrations).
- Per-task files (`progress.md`, `note_md` notes,
  `*.excalidraw` drawings, attachment bytes, `todo.json`)
  are *projections* derived from the DB. They can be regenerated
  by walking `TaskDirectoryStore`.
- Migrations live inline in `src/main/db/schema.ts`. Adding a
  column means adding a `(version, sql)` entry, never a hand-edit
  to a live DB.
- Tag names live in `tag_catalog` (DB-backed since v17). The
  previous `settings.tags` array in `${userData}/config.json` is
  imported exactly once and then ignored.

## Impact

- Cross-cutting changes (rename, archive, AI tool mutation) need
  only update the DB; file projections are best-effort and may be
  regenerated by the renderer.
- Backup / restore is straightforward: stop the app, copy
  `${dataDir}`, restart. No partial-write risk because file
  projections live in their own per-task directory and the DB row
  is the authoritative pointer.
- New file stores must register themselves in `src/main/files/`
  and resolve their directory through `TaskDirectoryStore`. No
  store is allowed to compute a directory from a current title.

## Boundaries

- This decision covers *business* state. Application settings
  (provider, API key, hotkey, theme) live in `${userData}/config.json`
  via `SettingsStore` and are not part of the DB.
- The DB has no FK constraint to on-disk files. A deletion of a
  task that succeeded at the DB layer but failed to remove the
  per-task directory leaves an orphan dir; a future compaction
  pass will collect those. (Not yet scheduled.)
- File projections may briefly lag the DB during heavy write
  bursts. The renderer does not need this consistency because the
  data hooks read from the DB, not from the files.
