# 开发 Agent 改进任务指导提示词

> 使用方法：复制下方提示词，将 `<任务编号>` 替换成
> `docs/product-and-dfx-improvement-backlog.md` 中的一个任务编号。
> 一次只能执行一个任务。

---

你现在是 `ai-todo-list` 项目的开发 Agent。

## 一、任务身份

- 独立任务编号：`<任务编号>`
- 独立任务名称：从 `docs/product-and-dfx-improvement-backlog.md` 中读取对应名称

这是一个独立任务。不要推断、继承或处理其他对话中的历史需求。

只实施 `<任务编号>` 明确规定的目标。任务清单中的其他条目只是背景，不属于本次范围，不得顺手实现。

## 二、开始前必须完成

1. 完整阅读根目录 `AGENTS.md`。
2. 执行 `git status --short`。
3. 阅读 `docs/product-and-dfx-improvement-backlog.md` 中 `<任务编号>` 的完整章节。
4. 阅读该章节列出的所有“必须阅读”文件。
5. 按任务领域阅读以下当前契约：
   - 任务创建或文件存储：`docs/task-creation-and-storage.md`
   - 系统边界或启动流程：`docs/architecture.md`
   - 架构治理背景：`docs/architecture-improvement-roadmap.md`
6. 记录现有未提交修改，区分哪些属于用户、哪些可能属于本任务。
7. 保护所有已有未提交修改，不覆盖、不回退、不删除、不擅自格式化无关文件。
8. 未经用户明确要求，不创建 Git 提交。

如果文档与当前源码冲突，以当前源码为准，并在实施前报告冲突，不得把规划中的目标状态描述成已经实现。

## 三、代码探索要求

如果 CodeGraph 可用：

1. 执行 `codegraph status --no-color`。
2. 索引过期时执行 `codegraph sync --no-color`。
3. 使用具体的用户行为和数据流执行 `codegraph context`，不要只输入宽泛关键词。
4. 对核心符号执行 `codegraph node`、`callers`、`callees` 或 `impact`。
5. 实施完成后对改动文件执行 `codegraph affected`，辅助定位受影响测试。

如果 CodeGraph CLI 因工作区外路径被沙箱拒绝：

- 不绕过安全限制；
- 按运行环境申请必要权限，或使用项目本地调用方式；
- 如果仍不可用，立即回退到 `rg` 和人工调用链分析，不得停止工作。

无论 CodeGraph 是否可用，都必须用 `rg` 补查：

- IPC 通道字符串及其声明、调用和注册；
- `app:*`、`ai:*` 等事件名称；
- Electron 生命周期和事件监听；
- React `useEffect`、订阅清理、状态和闭包；
- `import()` 动态导入；
- `resources/dsh/cordis.yml` 中的插件、工具和行为约束；
- preload 暴露的 API；
- CSS class、CSS module 和布局关系；
- 文件路径、迁移、重命名和清理逻辑。

至少人工核查下列完整链路中与任务相关的部分：

```text
Renderer 组件
  → preload facade
  → IPC Registry/Channel
  → main handler
  → Repo/Service
  → SQLite 或文件投影
  → 数据变化事件
  → renderer hook/state
  → 最终 UI
```

AI 相关任务额外核查：

```text
AIPane
  → ai.ask
  → ai-handlers
  → DSH runtime
  → DSH tool
  → Repo/Store
  → stream/history projection
  → AIPane
```

## 四、实施前输出

在修改代码前，先给出一份简短但具体的实施说明，包括：

1. 当前真实实现。
2. 问题根因。
3. 入口文件、核心符号和调用链。
4. 可以复用的组件、Repo、Store、IPC 或 DSH 能力。
5. 预计修改的文件。
6. 明确不修改的范围。
7. 数据流、状态流和错误流设计。
8. 兼容性和回归风险。
9. 验证计划。

如果缺少会实质改变方案的产品决策，停止实施并提出一个明确问题。不要用占位行为替用户做决定。普通实现细节不足时，应继续阅读源码并作最小、可逆、符合现有模式的判断。

## 五、通用架构约束

1. SQLite 是业务事实来源；文件是用户可见、耐久、可恢复的投影。
2. 一个任务只能有一个稳定的 `todos.storage_dir` 关联。
3. 所有任务文档、绘图、缩略图和附件必须通过同一个 `TaskDirectoryStore` 关联解析。
4. 不得根据任务当前标题在每次访问时重算目录。
5. 重命名目录失败时继续使用原关联，不创建替代目录。
6. `plannedFor` 表示本地日期的 Today 归属；它与 `dueAt` 截止时间相互独立。
7. `project` 是遗留 nullable 字段，不是可用产品实体，不得在新功能中暴露或写入。
8. 表单创建必须直接调用 `todo.create`，不经过 AI。
9. AI 创建任务必须显式使用 `intent: 'create-task'`。
10. 普通 AI 对话保持普通对话，不能因为文本类似待办而自动创建。
11. 不得发明任务 ID 或 `parentId`；必须查询真实任务。
12. 优先复用已有领域对象和写入路径，不创建功能重复的服务。
13. 新旧实现过渡期间只能保留一个业务写入源，不双写两个事实来源。
14. 不在 renderer 复制主进程业务规则。
15. 不向 renderer、日志、诊断包或错误提示泄漏 API Key、内部堆栈或不必要的绝对路径。

## 六、任务专属要求

严格按照 `docs/product-and-dfx-improvement-backlog.md` 中 `<任务编号>` 的以下内容实施：

- 目标；
- 当前问题或根因；
- 必须阅读；
- 预计修改范围；
- 实施要点或 MVP 范围；
- 非目标；
- 验收标准。

如果该任务在清单中只有简要说明，必须先把它补充为本次实施说明中的具体设计，但不要修改任务清单本身，除非用户明确要求同步文档。

## 七、编码规则

- 使用 `apply_patch` 做聚焦编辑。
- 保持现有命名、类型、错误处理和模块风格。
- 避免无关重构和批量格式化。
- 不新增重复组件、重复 hooks、重复 IPC facade 或重复存储解析器。
- 数据结构变化必须完整覆盖 shared type、schema/migration、Repo、IPC、preload 和 UI。
- IPC 变化必须完整覆盖 registry、请求响应类型、preload、handler、调用方和事件订阅。
- AI 工具变化必须核查 DSH runtime、权限分层、工具展示和 `cordis.yml` 行为约束。
- 文件存储变化必须覆盖稳定重复解析、遗留目录采用、成功重命名、失败重命名和所有文档类型。
- React effect 必须正确清理监听器、计时器、observer 和异步生命周期。
- 长任务必须支持取消或明确不可取消；重试必须防止重复并发执行。
- 任何 destructive 操作都必须有精确目标、确认或可恢复策略。

## 八、验证步骤

至少执行：

```bash
pnpm typecheck
pnpm build
```

并根据任务执行：

1. 与改动模块直接相关的现有 Vitest 测试。
2. 涉及关键用户链路时执行相关 Playwright 测试。
3. `git diff --check`。
4. `git diff --stat` 和完整 `git diff`。
5. `git status --short`。
6. 如果 CodeGraph 可用，执行 `codegraph affected <改动文件>`。
7. 按任务清单逐条验证验收标准。

只有实际执行过的命令和手工操作才能报告为“通过”。不能把“代码看起来正确”表述为手工验证通过。

如果验证失败：

- 先判断是否由本任务改动导致；
- 修复本任务引入的问题；
- 如果是已有问题，提供命令、错误摘要和与本任务无关的证据；
- 不借机修改无关代码。

## 九、完成标准

任务只有在同时满足以下条件时才算完成：

1. `<任务编号>` 的目标和验收标准均已实现。
2. 没有实现任务清单中的其他独立任务。
3. 真实调用链各层已保持一致。
4. 没有新增第二套事实来源或重复写路径。
5. 原有未提交修改被完整保留。
6. 类型检查通过。
7. 正式构建通过。
8. 相关自动化测试通过，或清楚记录无法运行的外部原因。
9. 实际 Git diff 只包含本任务所需修改。
10. 没有未经授权创建提交。

## 十、最终交付报告格式

请严格按以下结构报告：

### 1. 完成结果

- 任务编号和名称
- 已实现的用户可见结果
- 是否满足全部完成标准

### 2. 根因与设计

- 修改前的真实实现
- 问题根因
- 最终选择的方案
- 放弃的备选方案及原因

### 3. 调用链与状态流

- 入口
- Renderer → Preload → IPC → Main → Repo/Store → DB/File → Event → UI 链路
- AI、重试、失败和取消路径（如适用）

### 4. 修改文件

对每个文件说明：

- 路径
- 修改内容
- 修改原因

### 5. 兼容性与风险

- 数据兼容性
- IPC/API 兼容性
- 性能影响
- 安全和隐私影响
- 仍存在的已知限制

### 6. 验证结果

列出每个实际执行的命令及结果：

- CodeGraph 探索或回退方式
- 类型检查
- 单元测试
- E2E 测试
- 正式构建
- 手工验证
- `git diff --check`

### 7. Git 状态

- 本任务新增或修改的文件
- 开始前已有的未提交文件
- 是否创建提交；默认应为“否”

### 8. 后续建议

只列出与本任务直接相关、但明确未纳入本次范围的事项。不得声称已实现。
