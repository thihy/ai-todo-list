# 架构改进路线与开发 Agent 任务清单

> 状态：规划文档，不代表任务已经实现。
>
> 目标：在不停止产品迭代的前提下，逐步收敛模块边界、数据一致性、AI 集成、启动性能和工程契约。
>
> 本文只定义架构治理工作。具体功能需求应建立独立任务，不要借架构任务顺带修改用户行为。

## 1. 当前判断

项目的技术选型可以继续使用：Electron、React、SQLite、文件投影和 DSH 都符合当前产品形态。主要问题是功能增长后，多个模块同时承担了编排、业务规则、状态管理和展示职责。

当前重点关注的高复杂度文件包括：

| 文件 | 当前职责 |
| --- | --- |
| `src/main/index.ts` | Electron 生命周期、数据层装配、IPC、窗口、AI、SDK、托盘和维护任务 |
| `src/main/dsh/dsh-runtime.ts` | DSH 启动、Agent、会话、历史投影、工具注册和人机协作 |
| `src/renderer/panes/AIPane.tsx` | 会话、流式回答、工具、审批、滚动、输入和展示 |
| `src/renderer/panes/TodoListPane.tsx` | 数据查询、树结构、任务操作和完整列表展示 |
| `src/renderer/components/SettingsModal.tsx` | 全部设置领域及其保存状态 |
| `src/renderer/hooks/useTodoListApi.ts` | IPC 客户端、查询、缓存、事件和部分业务状态 |

这些文件不应按行数机械拆分。拆分标准是职责、生命周期和变更原因是否一致。

## 2. 目标边界

建议逐步形成以下结构，不要求一次性搬迁：

```text
features/
  tasks/
  tags/
  documents/
  conversations/
  ai/
  settings/

platform/
  electron/
  ipc/
  database/
  filesystem/
  startup/

integrations/
  dsh/
    runtime/
    tools/
    projection/
    presentation/
```

目录不是目标本身。目标是让一个业务能力的规则、用例和适配器能够被单独理解、修改和验证。

## 3. Agent 执行规则

每个开发 Agent 开始任务前必须：

1. 阅读根目录 `AGENTS.md` 及任务涉及的架构文档。
2. 检查 `git status --short`，保留其他任务的未提交改动。
3. 使用 CodeGraph 查入口、调用方和影响范围，再用 `rg` 补充字符串事件、IPC 通道、React 闭包和 CSS 关系。
4. 先记录现状和边界，再实施；不要为了“顺手整理”扩大任务范围。
5. 新旧路径过渡时只保留一个写入源，避免双写。
6. 完成类型检查和正式构建。只有实际执行过的交互才能声明为手动验证通过。
7. 一个任务一个提交。提交只包含该任务明确涉及的文件。

推荐的 CodeGraph 流程：

```text
codegraph sync
codegraph context <任务描述>
codegraph impact <核心符号>
rg 补充动态关系
阅读源码并实施
codegraph affected <改动文件>
类型检查与构建
```

CodeGraph 是导航工具，不是事实来源。它可能遗漏闭包、字符串注册和动态导入，也可能把类型依赖识别为调用关系。

## 4. 里程碑与依赖

```text
A 架构基线
├── B 启动生命周期
├── C IPC 契约
├── D 统一应用服务与文件投影
├── E 渲染端数据层
└── F AI / DSH 边界
     └── G AI 界面拆分

D ──> H 标签领域化
B + E ──> I 首屏性能治理
A..I ──> J 文档与运行保障收尾
```

`A` 是后续任务的共同前置。其他分支在文件不冲突时可以并行。

## 5. 任务清单

### ARCH-01 建立可信架构基线

**目标**

让架构文档准确描述当前系统，为后续开发和 AI Agent 提供可靠上下文。

**范围**

- 重写 `docs/architecture.md` 中已经过时的启动、DSH、存储、窗口安全、Renderer 和 IPC 内容。
- 保留 `docs/task-creation-and-storage.md` 作为任务存储专项契约，并从主架构文档链接。
- 将历史提案明确标为历史，不再让其充当当前实现说明。
- 增加简短 ADR，记录下列决定：
  - SQLite 是业务事实来源，文件是可重建投影；
  - AI 创建意图必须显式传递；
  - DSH 通过集成层进入应用；
  - Core 与 AI 使用独立启动状态；
  - 标签目录变化不得重写历史任务标签。

**不做**

- 不修改运行代码。
- 不在文档中描述尚未落地的目标架构为“当前实现”。

**完成标准**

- 文档中的文件路径、API 名称和安全设置都能在当前源码中找到。
- “当前状态”和“目标状态”明确分开。
- 删除或修正已失效的 preload 命名空间引用（现迁移至 `window.todoList`），并清理旧 Sidebar、旧 flat-file 和旧 shim 描述。

### ARCH-02 收敛主进程组合根

**依赖**：ARCH-01

**目标**

让 `src/main/index.ts` 只负责生命周期和服务装配。

**实施方向**

- 提取 `DataServices`：设置、数据库、Repo、文件存储。
- 提取 `IpcModules`：按 tasks、documents、settings、ai、app 注册。
- 提取 `BackgroundServices`：AI、SDK、归档、提醒、托盘。
- 提取 `WindowManager`：主窗口、捕获窗口及关闭行为。
- 每个服务暴露明确的 `start`、`ready` 和 `dispose` 契约。
- 应用退出时由统一 disposer 逆序释放资源。

**完成标准**

- `index.ts` 不再包含具体业务处理器实现。
- 启动顺序和依赖可以从组合代码直接读出。
- 单个后台服务失败不会阻止其他无依赖服务启动。
- 没有重复注册 IPC、定时器或 Electron 事件。

### ARCH-03 建立正式启动状态机

**依赖**：ARCH-01；可与 ARCH-02 联动

**目标**

尽早显示可响应的应用壳层，并将 Core 与 AI 的启动状态分开。

**状态建议**

```text
shell-ready -> core-loading -> core-ready
                         \-> core-failed
core-ready -> ai-loading -> ai-ready
                        \-> ai-unavailable
```

**实施方向**

- 启动状态模块属于 `platform/startup`，不要绑定到某个 React 页面。
- 在 React 和重型资源加载前显示轻量启动页。
- Core 只等待任务管理必需的数据库、存储和 IPC。
- AI、SDK、历史整理和维护任务在 Core 之后独立启动。
- AI IPC 应在固定阶段注册；未就绪时返回统一状态，而不是出现未注册通道。
- 记录阶段耗时，用实测决定后续优化。

**完成标准**

- 启动期间窗口可移动、可关闭，不表现为系统未响应。
- AI 初始化失败不阻止任务管理。
- 错误状态不会无限停留在“正在启动”。
- 构建产物冷启动阶段耗时有可对比记录。

### ARCH-04 让 IPC 契约成为唯一来源

**依赖**：ARCH-01

**目标**

减少 IPC 名称、类型、Preload 和 Handler 注册之间的手工同步。

**实施方向**

- 从一份 Registry 派生运行时通道允许列表。
- 为请求、响应和推送事件分别建立类型契约。
- Preload facade 由契约包装，避免组件理解路由内部格式。
- 增加启动时完整性检查：声明但未注册、注册但未声明均明确失败。
- 将错误分类为参数、未就绪、领域失败、基础设施失败和未知错误。

**完成标准**

- 新增普通 IPC 不需要在多个独立字符串列表中重复登记。
- Renderer 不接触原始 `ipcRenderer`。
- 所有错误有稳定 code，界面不依赖英文 message 判断业务分支。

### ARCH-05 建立任务应用服务

**依赖**：ARCH-02、ARCH-04

**目标**

所有任务创建和更新入口共享相同业务流程。

**实施方向**

- 建立 `TaskApplicationService`，封装创建、更新、归档、删除和恢复用例。
- UI、AI 工具、快捷捕获、剪贴板和 SDK 只调用应用服务。
- Repo 仅处理数据库模型，不负责 Electron 通知或界面广播。
- 应用服务统一触发文件投影、搜索更新和变更事件。
- 输入校验与领域规则集中，避免入口间行为漂移。

**完成标准**

- `repo.create + md.writeBody` 等组合不再散落在多个入口。
- 每个写操作只有一个权威执行路径。
- 新增任务入口无需复制存储初始化逻辑。

### ARCH-06 建立可靠的文件投影层

**依赖**：ARCH-05

**目标**

明确并落实“SQLite 为事实来源、文件为投影”的一致性策略。

**实施方向**

- 定义统一 `ProjectionService`，管理 `todo.json`、`progress.md`、笔记、绘图和附件投影。
- 文件采用临时文件加原子替换，避免进程中断留下半文件。
- 投影失败有记录、重试和重建入口。
- 启动迁移与正常读写不能并行操作同一文件集合。
- 迁移部分失败时保留可重试状态，不能写成永久成功。
- 明确读取策略：正常读取以数据库还是文件为准；文件缺失时如何恢复。

**完成标准**

- 数据库成功而文件失败时，系统能够发现并修复投影。
- 文件损坏或缺失不导致权威内容静默变空。
- 旧布局迁移可以重复运行且不会与用户写操作竞跑。

### ARCH-07 统一 Renderer 数据访问层

**依赖**：ARCH-04

**目标**

组件只消费查询和命令，不直接管理 IPC 生命周期。

**实施方向**

- 提供 typed client、query 和 command 三层。
- 统一加载、失败、重试、取消和乐观更新语义。
- 用实体或查询键做精准失效，逐步替换粗粒度全量刷新。
- 将组件中的直接 `window.todoList` 调用迁到命令或查询 Hook。
- 选择轻量自研 Store 或 TanStack Query 前，先用两个复杂页面做验证。

**完成标准**

- 新组件不直接访问 `window.todoList`。
- 相同数据在同一窗口内有统一缓存和刷新规则。
- 保存失败不会被吞掉，草稿和持久化状态明确分开。

### ARCH-08 拆分任务列表与设置界面

**依赖**：ARCH-07

**目标**

按业务职责拆解大型 Renderer 模块。

**实施方向**

- `TodoListPane` 拆为列表控制器、树投影、行操作和纯展示组件。
- 树展开状态、今日计划和任务写操作由控制器管理。
- `SettingsModal` 只负责导航、关闭保护和统一保存反馈。
- 模型、标签、配色、数据目录、提醒分别成为独立设置模块。
- 设置模块通过统一 Settings command 保存，不互相了解字段细节。

**完成标准**

- 任务行和设置子页面可以独立渲染。
- 模态框不保存某个具体设置领域的草稿。
- 新增设置分类不需要修改多个现有分类内部实现。

### ARCH-09 建立稳定的 DSH 集成层

**依赖**：ARCH-01、ARCH-04

**目标**

将 DSH 版本变化限制在集成目录内，并优先使用其公共协议和组件。

**实施方向**

- 分离 Runtime、Conversation、Tool Registry、Projection 和 Presentation。
- 定义应用内部稳定的 `AiTurnBlock`，DSH 原始事件只在投影层出现。
- 工具名称、输入、结果和生命周期由 callId 驱动的统一模型表达。
- 领域工具负责业务语义，DSH 适配器负责协议转换。
- 记录本地复制的 DSH 组件来源、版本和差异。
- 能通过公共组件或薄适配实现时，逐步删除本地分叉。

**完成标准**

- DSH 包升级不要求直接修改 `AIPane` 的业务状态。
- 实时消息与历史消息经过同一投影模型。
- 新增工具无需在多个 Renderer switch 中重复登记展示规则。

### ARCH-10 将 AI 面板改为组合层

**依赖**：ARCH-07、ARCH-09

**目标**

让 `AIPane` 只组合会话、消息、交互和输入模块。

**建议模块**

- `useConversationController`
- `useStreamingTurn`
- `useHumanInteraction`
- `useConversationHistory`
- `ConversationHeader`
- `ConversationTimeline`
- `ConversationComposer`

滚动跟随保持独立 Hook，不与消息归并或工具状态相互修改。

**完成标准**

- 会话状态由 reducer 或专门 Store 管理，有明确状态转换。
- 组件切换不会丢失当前流式轮次、审批或阅读位置。
- `AIPane` 不直接解析 DSH 原始事件。

### ARCH-11 标签领域化

**依赖**：ARCH-05、ARCH-06；功能设计需同时遵守标签专项需求

**目标**

支持标签统计、合并、停用和历史隔离，而不是继续把标签当成设置字符串数组。

**领域规则**

- 标签目录保存身份、名称、颜色和启停状态。
- 有效任务统计排除已删除和已归档任务。
- 重命名和合并只修改有效任务关联。
- 已删除或已归档任务保留操作发生时的标签显示。
- 清理未使用标签采用逻辑停用，不删除历史关联。
- 语义相似只生成建议，由用户确认合并目标。

**完成标准**

- 标签的创建、修改、合并和停用由一个应用服务执行。
- 设置、任务编辑和 AI 创建共享同一标签目录。
- 恢复历史任务不会静默把原标签替换为后来的合并结果。

### ARCH-12 首屏资源与交互性能治理

**依赖**：ARCH-03、ARCH-07

**目标**

基于测量缩短冷启动和首屏可交互时间。

**实施方向**

- 建立入口包、重型编辑器和 AI 面板的 bundle 基线。
- 确认动态导入没有被其他静态导入抵消。
- 绘图、Markdown 高亮、Mermaid、统计和设置按实际访问懒加载。
- 流式 Markdown、工具卡片和滚动测量采用批处理，避免每个 token 全量重算。
- 优化结果用阶段耗时和 bundle 变化衡量，不以“增加启动页”代替性能改善。

**完成标准**

- 启动入口不包含当前页面无需使用的编辑器和绘图依赖。
- 冷启动、首屏和首次打开重型页面分别有耗时记录。
- 懒加载失败有局部错误界面，不导致整窗空白。

### ARCH-13 Electron 平台安全收敛

**依赖**：ARCH-02、ARCH-04

**目标**

将 Electron 权限、协议和外部资源访问集中管理。

**实施方向**

- 评估并恢复 Renderer sandbox；若必须关闭，记录不可替代原因。
- 收紧 CSP，逐步移除不必要的 `unsafe-inline`。
- 自定义协议只允许访问明确根目录内的文件，规范化后检查路径边界。
- 外部链接、附件和文件选择都经过统一校验。
- Renderer 仅通过最小化 Preload API 获得能力。

**完成标准**

- 协议不能通过编码路径访问允许根目录之外的文件。
- 外部 URL 和本地文件能力有清晰白名单。
- 安全配置与架构文档一致。

### ARCH-14 运行保障与可观测性

**依赖**：ARCH-02、ARCH-03、ARCH-06、ARCH-09

**目标**

让启动、投影、迁移和 AI 失败可以被定位，而不泄露用户数据。

**实施方向**

- 统一结构化日志字段：模块、阶段、错误码、耗时和 invocationId。
- 禁止记录 API key、完整提示词、任务正文和绝对敏感路径。
- 为启动失败、迁移失败、投影积压和 AI 不可用提供诊断摘要。
- 定义健康状态，但不把“配置完整”“网络探测”和“实际调用成功”混为一谈。

**完成标准**

- 用户报告问题时可以通过一个诊断摘要确认失败阶段。
- 日志中的错误码可以回到明确模块和恢复建议。

## 7. Definition of Done

一个架构任务只有满足以下条件才算完成：

- 职责边界比改动前更清晰，没有新增平行写入路径。
- 旧入口已经迁移或有明确弃用计划。
- 错误和未就绪状态具有稳定语义。
- 文档同步描述真实实现。
- 类型检查和正式构建通过。
- 关键交互由开发者或 Agent 实际验证，并如实记录未验证项。
- 提交不包含其他开发任务的工作区改动。

## 8. 推荐领取顺序

近期优先级：

1. ARCH-01 架构基线。
2. ARCH-03 启动状态机，承接当前启动页面工作。
3. ARCH-04 IPC 契约。
4. ARCH-05 与 ARCH-06，稳定所有任务写入和文件投影。
5. ARCH-11 标签领域化，承接标签管理新需求。
6. ARCH-09 与 ARCH-10，控制 AI 模块继续增长。
7. ARCH-07 与 ARCH-08，逐步收敛 Renderer。
8. ARCH-12、ARCH-13、ARCH-14 完成平台治理。

不要同时启动会修改同一核心文件的任务。例如 ARCH-02、ARCH-03 和 ARCH-05 都可能修改 `src/main/index.ts`，应按顺序落地或事先划定文件所有权。
